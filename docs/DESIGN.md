# 設計

ML-ModelControl の設計の方針をまとめる.

## 目的

PyTorch (と互換のライブラリ) で作れるモデルの部品を登録簿として持ち, 部品をつないだ定義から `nn.Module` を組み立てる.
モデルを Python で書かずに, 定義 (YAML か JSON) を書くか, GUI (ML-CreateArchitecture) で部品を置いてつなぐだけで作れるようにする.

- 部品の単位は 1 つに決めない. `nn.Linear` のような層, 足し算や連結のような演算, PyTorch Geometric のグラフニューラルネットワークの層, Hugging Face, torchvision, timm などの学習済みのモデルを, 同じ登録簿で同じように扱う
- GUI が必要とすること (部品の一覧と引数の説明, つなぎ方の確認, 各部品の出力の形, パラメータ数) は, このライブラリが返す. GUI は描画と編集だけを受け持つ
- 学習はこのライブラリの対象外. 組み立てたモデルは普通の `nn.Module` なので, ML-Found などで学習できる

## 全体の中での役割

「機械学習を全て GUI 上で行う」アプリ (問題の設定, データの分析, モデルの作成・選定, モデルの学習・評価, 推論の段階に分けて作ることを目指している) のうち, 「モデルの作成・選定」の段階でライブラリを受け持つ. 画面は ML-CreateArchitecture.

- モデルの定義の形 (下の「モデルの定義の形」) を持ち, `format_version` で版を付ける. 定義を作る側 (GUI か手書き) と使う側 (学習のスクリプト) は, 主にこの形でつながる (コードとして持ち出す場合は Python に書き出せる)
- 他の段階のライブラリのコードを前提にしない. ML-Found で学習する場合は, 学習のスクリプトが定義から組み立てた普通の `nn.Module` をそのまま使う (README の「ML-Found で学習する」)

## 用語

| 用語 | 意味 |
| --- | --- |
| 部品 (unit) | 登録簿にある, モデルの 1 つの単位. 名前 (`nn.Linear`, `op.Add`, `pyg.GCNConv`, `hf.AutoModel` など), 引数, 入力と出力の口を持つ |
| ノード (node) | モデルの定義の中で使う部品の 1 つ. 名前 (id), 部品の名前, 引数の値, 入力のつなぎ先を持つ |
| 口 (port) | 部品の入力と出力の名前. `nn.Linear` は入力 `input`, 出力 `out`. GCN の層は入力 `x`, `edge_index`, `edge_weight` (省略可) |
| モデルの定義 (graph) | モデルの入力, ノード, 出力をまとめたもの. YAML か JSON で保存する |

## モデルの定義の形

ノードとつなぎ方のグラフ (分岐と合流のある有向非巡回グラフ) にする.

一番上の項目のうち, `inputs`, `nodes`, `outputs` は必須. `format_version` (書かなければ版 1), `name`, `description`, `subgraphs`, `ui` は省ける. 他の項目は誤り (`unknown_key`).
順に並べるだけのモデルも, 前のノードにつなぐだけなので同じ形で書ける.

```yaml
format_version: 1
name: residual_mlp
description: 残差のつなぎ方を持つ全結合のモデル
inputs:
  x: {shape: [4, 16]}                  # 形の推定に使う例の形 (書いたとおりの形)
nodes:
  fc1:
    unit: nn.Linear
    params: {in_features: 16, out_features: 16}
    inputs: {input: x}                 # 口の名前: つなぎ先
    ui: {x: 120, y: 80}                # GUI の位置など (組み立てでは使わない)
  act:
    unit: nn.ReLU
    inputs: fc1                        # 必須の口が 1 つの部品は口の名前を省略可
  add:
    unit: op.Add
    inputs: {xs: [x, act]}             # 可変の数の口はリスト (順に意味がある)
  head:
    unit: nn.Linear
    params: {in_features: 16, out_features: 3}
    inputs: add
outputs:
  logits: head
```

- つなぎ先は「入力の名前」か「ノードの名前」. 出力が複数の部品は「ノードの名前:口の名前」(例: `lstm:output`) で選ぶ. 出力が複数の部品を口の名前なしで参照するとエラー
- `inputs` の口は書く順に意味は無い. 省略できる口 (GCN の `edge_weight` など) は書かなくてよい. `inputs: fc1` の省略形は, 必須の口がちょうど 1 つの部品だけで使え, その口につなぐ
- `params` は部品を作るときの引数 (`__init__`), `forward_params` は呼び出すときの設定の値 (`nn.MultiheadAttention` の `need_weights` など). どちらも JSON の値 (数, 文字, 真偽値, null, それらのリスト) だけを書ける
- `outputs` が 1 つなら, 組み立てたモデルはテンソルを返す. 2 つ以上なら名前をキーにした辞書を返す. 組み立てたモデルは, 入力を定義の順の位置か, 名前のキーワードで受け取る
- ノードには版 2 で `train`, `eval_mode`, `zero_init`, `weights`, `share` を書ける (下の「パラメータの状態」)
- `ui` (ノードごとと, 一番上) と `description` は自由に書け, 組み立てでは使わず, 保存では残す. それ以外の知らない項目はエラーにする (書き間違いを見つけるため)

### 部分モデル (subgraphs)

保存したモデルの定義を, 別の定義の中で 1 つの部品として使える. 定義の一番上の `subgraphs` に名前と定義を書き, ノードの `unit` に `sub.<名前>` と書く.

```yaml
subgraphs:
  block:                               # 部分モデルの名前
    description: 残差のブロック
    inputs: {x: {}}                    # 口になる (形は書かなくてよい)
    nodes:
      fc: {unit: nn.Linear, params: {in_features: 16, out_features: 16}, inputs: x}
      add: {unit: op.Add, inputs: {xs: [x, fc]}}
    outputs: {y: add}
nodes:
  block1: {unit: sub.block, inputs: x}
  block2: {unit: sub.block, inputs: block1}   # 同じ部分モデルを何度も使える (重みは別)
```

- 部分モデルの入力は入力の口 (全て必須. 部分モデルの入力の順に位置で渡す), 出力は出力の口になる (出力が 2 つ以上なら辞書のキーで取り出す). 引数は持たない. 書き出すコードのクラスの名前は, 部分モデルの名前を `_` で区切った語の頭を大文字にしたもの (`res_block` は `ResBlock`. 識別子にならない場合は頭に `Subgraph` を付ける)
- 部分モデルの定義は, `format_version` と `subgraphs` を除いて普通の定義と同じ形. 入力の `shape` は書かなくてよく, 書いても形の推定には使わない (形は前のノードから決まる). 部分モデルの中で別の部分モデル (`sub.<名前>`, 同じ `subgraphs` の中のもの) を使え, 互いに使い合う循環は誤り
- **参照ではなく写す**: 部分モデルは, 元の定義のファイルを参照せず, 定義の中に写して持つ. 1 つのファイルだけで組み立てられ (学習のスクリプトに渡すのも 1 つ), 元のファイルを後から変えても, 保存した重み (`state_dict`) と合わなくなることがない. 写すには `embed_subgraph(spec, 名前, 写す定義)` を使う. 写す定義の部分モデルも同じ名前のまま一緒に写す (同じ名前で中身の違うものがあれば誤り). 元の定義を直した後に写し直す場合は `replace=True` で置き換える (一緒に写す部分モデルも, 同じ名前のものは写す定義の中身に置き換える)
- 組み立てたモデルでは, 部分モデルのノードは中に `GraphModel` を持つ. `state_dict` のキーは `nodes.block1.nodes.fc.weight` のようになる
- 確認では, 部分モデルの中の誤りを `node` が `None`, `subgraph` が部分モデルの名前, `location` が `subgraphs.<名前>.nodes.<ノード>.<場所>` (ノードに付かない誤りは `subgraphs.<名前>.<場所>`) の誤りとして返す. それを使うノードは使えない部品 (`unavailable_unit`) の誤り, 定義に無い部分モデルを使うノードは `unknown_subgraph` の誤りになる. 使われない部分モデル (本体から使う部分モデルをたどって届かないもの) は注意 (`unused_subgraph`. `location` は `subgraphs.<名前>` で, `subgraph` はその名前). どこからも使われない部分モデルでも, 中に誤りがあれば定義全体の誤りになり, 組み立てと書き出しはできない
- 形の推定は, 部分モデルを使うノードについて, その出力の口ごとの形とパラメータ数 (中の全てのノードの合計) を返す (中のノードごとの形は返さない). 部分モデルの中の誤りは, それを使うノードとその先だけを止める. 部分モデルの中で計算の誤りが起きた場合は, 誤りの文に中のどのノードで起きたかを添える (Python 3.11 以上). 計算に失敗したノードの誤りの文には, 入った値の口ごとの形と型を添える (「(入った値: input [4, 16] float32)」. 形や型の合わない誤りを, 前のノードを見に行かずに直せるように). よくある食い違い (入る値の最後の次元と `in_features`, `normalized_shape`, チャネルと `in_channels`, `num_features`, `num_channels`. 番号を受け取る `nn.Embedding` への小数, 小数を受け取る層への整数) には「→ 入る値の最後の次元 16 と in_features 8 が合いません (in_features を 16 にするか, 前のノードを直してください)」のような直し方を添える
- 書き出すコードでは, 使う部分モデルごとに 1 つのクラスを書く (中で使う部分モデルのクラスを先に置く. 使われない部分モデルは書かない). 部分モデルのクラスの名前が本体のクラスの名前と重なる場合はエラー
- GUI のために, 定義の中の部分モデルの部品の一覧を `describe_spec_units(spec)` で返す (`describe_units` と同じ形で, 部分モデルの部品だけを定義に書いた順に. `describe_units()` の一覧に加えて使う). 分類は `sub`, 出どころは `subgraph`. 中に誤りのある部分モデルも, 使えない部品 (`available` が `false`) として含める

### パラメータの状態 (版 2)

学習済みのモデルを部品にして新しい層だけを学ぶ形 (ControlNet や LoRA のような足した枝, 頭だけの学習, 埋め込みの共有, 2 塔の共有の塔) を, 学習のスクリプトを書かずに定義に書けるようにする. ノードに 5 つの項目を足す (部分モデルの中のノードにも書ける). どれも 1 回の順伝播の計算は変えず, パラメータの状態 (学習するか, 初期値, どこから読むか, 誰と同じか) だけを決める. 損失, 更新の順, 最適化手法の設定は学習のスクリプトに残す.

```yaml
format_version: 2
nodes:
  backbone:
    unit: sub.encoder
    inputs: x
    train: false                       # 凍結 (パラメータの requires_grad を偽に)
    eval_mode: true                    # BatchNorm の統計と Dropout も評価の形のまま
    weights:                           # 外部の重みの一部の読み込み
      path: weights/base.pt            # ファイル (hub か unit でも)
      remap:                           # 上から見て最初に当たった 1 つで付け替え
        - {from: "model.blocks.", to: "nodes."}
        - {pattern: "^model\\.layer\\.(\\d+)\\.", to: "nodes.block\\1.", offset: -6}  # 層 6 から 11 を block0 から 5 に (0 から 5 は負になり当たらない)
      strict: false                    # 既定は true
  control_out:
    unit: nn.Linear
    params: {in_features: 16, out_features: 16}
    inputs: backbone
    zero_init: true                    # 全てのパラメータを 0 に ([weight] のように名前も可)
  tower_b:
    unit: sub.tower
    inputs: item
    share: tower_a                     # ノード全体を共有 (同じ部品を 2 回使う)
  head:
    unit: nn.Linear
    params: {in_features: 16, out_features: 1000}
    inputs: backbone
    share: {weight: embed.weight}      # パラメータごとの共有 (埋め込みと出力の重みの共有)
```

- **凍結** (`train`. 真偽値, 既定は真): 偽ならノードの全てのパラメータの `requires_grad` を偽にする. 部分モデルのノードに書けば中の全てのノードを凍結する. 最適化手法には `model.parameters()` をそのまま渡してよい (勾配が来ないパラメータは更新されない. 渡すものを絞るなら `requires_grad` が真のものだけ). 名前ごとの一部の凍結は今は書けない (要る例が出たら足す)
- **評価の形** (`eval_mode`. 真偽値, 既定は偽): 真ならノードを, モデル全体を `train()` にしても評価の形のままにする (BatchNorm は保存した平均と分散を使って更新せず, Dropout は落とさない). 凍結とは別の項目 (凍結はパラメータ (勾配) の話で, BatchNorm の統計はパラメータではない状態 (バッファ) のため). 凍結しても統計は学習の形で動き続けるのが PyTorch の普通の動きで, 凍結した骨格の統計も止めたいか (小さなバッチで統計が壊れるのを防ぐ) は場合による. 真偽値でなければ誤り (`invalid_state`. `train` も同じ). 既定は偽 (定義に書いていない振る舞いを足さないため). 確かめ (`validate`) は, `train: false` で `eval_mode` を書いていない BatchNorm の部品 (`nn.BatchNorm1d` など, 統計を持つ正規化) に注意 (`frozen_norm_stats`) を出す (中が見えない学習済みのモデルや部分モデルには出さない)
- **零初期化** (`zero_init`. 真偽値か, パラメータの名前のリスト. それ以外は誤り `invalid_state`): 作った後にパラメータを 0 にする. 名前は部品の `named_parameters()` の名前 (`weight`, `bias`, 部分モデルでは `nodes.fc.weight`). 足した枝の最後の層を 0 にして, 学習の始めは元のモデルの出力と同じにする使い方のため. 無い名前は組み立てで誤り. 部分モデルの中のノードに書いた項目は部分モデルを作るときに先に行うので, 外側のノードの `weights` で上書きされる (外側から 0 にする場合は外側のノードの `zero_init` に `nodes.fc.weight` のように書く)
- **外部の重み** (`weights`. 辞書): ファイルか学習済みのモデルの `state_dict` をノードに読む. 出どころは次の 3 つのどれか 1 つ
    - `path`: `torch.save` したファイル (`.pt`, `.pth`, `.bin`. `torch.load` の `weights_only=True` と `mmap=True` で読む. 古い形のファイルは mmap なしで) か `.safetensors` (safetensors が入っている場合. キーと形を先に読み, 読めるキーのテンソルだけを `safe_open` で読む). 相対のパスは, 定義をファイルから読んだ場合はそのファイルのディレクトリから, 辞書で渡した場合は `build_model` の `base_dir` (無ければ今のディレクトリ) から (部分モデルの中のパスも同じ. `embed_subgraph` でファイルから写す場合は, 写す定義の相対のパスを絶対のパスに直す). 読むファイルは, リンクをたどった先が, 相対のパスの元のディレクトリか, 環境変数 `ML_MODELCONTROL_WEIGHTS_DIRS` (パスの区切りで並べる) か `build_model` の `weights_dirs` のディレクトリの中にあるものだけ (定義を他の人から受け取った場合に, 手元の他のファイルを読まないため. 写した部分モデルの絶対のパスが外になる場合は足す). 読む前に大きさを確かめ, 上限 (既定 4 GiB. 環境変数 `ML_MODELCONTROL_WEIGHTS_MAX_BYTES` のバイト数) を超えれば誤り. 誤りの文には定義に書いたパスだけを出し, 手元の絶対のパスは出さない. `weights_only` で読めないファイル (テンソル以外の, 読むとコードを動かせる値を含むもの) は, `weights_only` を外す案内をせず, state_dict だけを保存し直すか safetensors にするよう案内する. `weights_only` が既定で真になった PyTorch 2.6 以上を依存にする
    - `hub` (Hugging Face の置き場の名前) と `file` (置き場の中のファイル. 必須) と `revision` (既定 `main`): huggingface_hub で取ってきて `path` と同じく読む. ライセンスは「学習済みの重みのライセンス」と同じ読み方で配布元から読み, 報告に添える
    - `unit` (登録簿の部品の名前) と `params`: その部品を (学習済みの重みを読む引数のまま. 外の乱数の状態を変えずに) 作り, その `state_dict` を使う (例: `timm.Model` の `resnet18` の学習済みの重みを部分モデルの骨格に). ライセンスは `pretrained_info` で読み, 報告に添える
    - `state_key` (省略可): ファイルの中身が `{"state_dict": ...}` のように入れ物の辞書の場合に, `state_dict` を取り出すキー (`.` で区切って入れ子も. `.` を含むキーは `[model.ema]` のようにリストで書く). 取り出した辞書の中に辞書があれば, 黙って除かずに誤り (入れ物のままで `state_key` の書き忘れのため). safetensors には書けない
    - `remap` (省略可. リスト): キーの付け替え. 前置きの置き換え `{from: "model.blocks.", to: "nodes."}` (部分モデルのノードのキーは `nodes.` で始まる) を基本にし, 番号を付け替える場合だけ正規表現 `{pattern: 正規表現, to: 置き換え (\1 などの参照可), offset: 整数 (省略可)}` を許す. 前置きも正規表現もキーの先頭から当てる (正規表現は `re.match`). 置き換えの参照 (`\1`, `\g<名前>`) は正規表現にあるグループだけ. `offset` は, 名前の無いグループがちょうど 1 つの正規表現で, 置き換えに `\1` (か `\g<1>`) を書いたときに, その番号に足して置き換える (`layer.6` から `layer.11` を `block.0` から `block.5` に読む, など). 足すと負になる番号 (12 層のファイルの `layer.0` から `layer.5` に -6) と数字でない番号では, その行は当たらないものとして次の行を見る (どの行にも当たらなければそのまま. 使わない重みに数える). `07` のように 0 で詰めた番号は幅を保つ. ファイルのキーごとに上から見て最初に当たった 1 つだけを使い, どれにも当たらないキーはそのまま. 空の前置き (`from: ""`) は全てのキーに当たる (全てのキーの頭に `to` を足す使い方. その下の行は使われない). 付け替えた後に同じキーになる 2 つのキーは誤り. 書き方の誤りは確かめで `invalid_weights`
    - `strict` (省略可. 真偽値, 既定は真): 読み込んだ後に報告を数え, 真なら形の違う重みか新しい重み (ノードにあってファイルに無い) が 1 つでもあれば誤り. 偽なら読めたものだけを読み, 残りは今の値 (乱数の初期値か零初期化) のまま. 使わない重み (ファイルにあってノードに無い) は, ファイルの一部だけを読むのがこの機能なので, どちらでも誤りにしない. 既定は真 (付け替えの書き間違いで黙って一部だけが読まれるのを防ぐため. 頭を差し替えるなど, 読めないものがあると分かっている場合に偽にする). どちらでも, 読めた重みが 0 個なら誤り
    - 報告 (`GraphModel.weights_report`): 読んだノードごとに `node` (部分モデルの中は `block1.fc` のように `.` でつなぐ), `source` (出どころの説明), `strict`, `loaded`, `mismatched`, `new`, `unused` (数), `mismatched_keys` (キー, ファイルの形, ノードの形), `new_keys`, `unused_keys` (付け替えた後のキー. どれも 50 個まで), `license` (`pretrained_info` と同じ形. ライセンスを読めない出どころ (`path`) は `None`), `warnings` (注意の文のリスト). 数はパラメータとバッファ (BatchNorm の統計など) の `state_dict` のキーで数える (`num_batches_tracked` は新しい重みに数えない. 古いファイルには無いため. 共有したパラメータの別のキーも, どれかが読めれば新しい重みに数えない. 共有した重みはファイルに 1 回だけ保存されることが多いため)
    - 読み込みは `build_model` の中で行う (`fetch=False` ではライセンスを読むのにネットワークを使わない. `load_weights=False` で読まない. 学習した重みを後から `load_state_dict` で読む場合に, 外部の重みを取りに行かないため). 確かめ (`validate`) と形の推定 (`infer`) は読まない (ネットワークとファイルを使わないため). 確かめは書き方 (出どころが 1 つか, 付け替えの形, 正規表現として読めるか, 参照と offset) だけを見る
    - 学習済みの重みを名前と版以外の所から読む引数 (`checkpoint_path`, `pretrained_cfg_overlay`, `pretrained_url`, `weights_url`, `pretrained_path`. 「学習済みの重みのライセンス」の上書きの引数と同じ) は, ノードの `params` にも `weights.params` にも書けない (誤り `unsafe_param`, `invalid_weights`. 版 1 の定義でも). 他のライブラリの読み込みは `weights_only` を確かめられないため, ファイルは `weights.path` で読む. timm の学習済みの重みの読み込み (`pretrained: true`) は timm に任せる (timm 1.0.31 は `weights_only=True` で読む. 依存の下限 `timm>=1.0` のうち, より古い版の読み方は確かめていない)
- **共有** (`share`): 2 つのノードで同じパラメータを使う. 書き方は 2 つ
    - ノードの名前 (`share: tower_a`): そのノードと同じ部品 (同じ `nn.Module`) を使う. 部品の名前が同じで, `params` も同じ値を書く (違えば誤り `share_mismatch`. 書かなければ他のノードと同じく必須の引数の誤り. 組み立ての途中までは自分の部品を作るため). 2 塔の共有の塔, 同じ層を 2 回通すなど. バッファ (BatchNorm の統計) と評価の形も共有する
    - パラメータの名前の辞書 (`share: {weight: embed.weight}`): キーはこのノードのパラメータの名前, 値は `<ノード>.<そのノードのパラメータの名前>`. 部品が違ってもよく (`nn.Embedding` の `weight` と出力の `nn.Linear` の `weight`), 形が同じでなければ組み立てと形の推定で誤り. 他のパラメータはこのノードのもの
    - 共有した重みは元のノードの設定 (`train`, `zero_init`, `weights`) に従う. パラメータごとの共有で, このノードと元のノードの `train` が違えば注意 (`share_train_mismatch`. このノードの `train` は共有しないパラメータだけに効く). 同じノードに `weights` を書いた場合は, 共有する名前を読む対象から除き (新しい重みにも数えない), ファイルにあれば使わない重みに数えて注意 (報告の `warnings` と `warnings.warn`) を出す. ノード全体を共有するノードには `train`, `eval_mode`, `zero_init`, `weights` を書けない (誤り `shared_setting`). パラメータごとの共有で, 共有する名前を `zero_init` に書くことも誤り. 共有する元は同じ定義 (本体か同じ部分モデル) のノードで, 自分自身と, 共有するノード (元が `share` を持つ. 連鎖) と, 書き方の誤りは `invalid_share`. 形の推定では, 共有の元が計算できないノードは共有するノードも `skipped`. 計算の順は変えない (共有はつなぎ方ではない)
    - 保存と読み込み: 共有は定義に書くので, 組み立てるたびに作り直される. `state_dict` には両方のノードのキーが同じ値で入り (PyTorch の普通の共有と同じ), `torch.save` で保存すると両方のキーが残る. `load_state_dict` は同じパラメータに 2 回書く (同じ値なので結果は同じ). safetensors は共有したテンソルをそのままは保存できず (`save_file` は誤り), `save_model` は片方のキーだけを残すので, 読むときは片方のキーで足りる (外部の重みの報告でも, 共有したパラメータの別のキーは新しい重みに数えない). 形の推定と `model.parameters()` は共有したパラメータを 1 回だけ数える
- 組み立ての順: 部品を作る → 外部の重みを読む → 零初期化 → 凍結 → 共有 → 評価の形. 外部の重みを読んだノードの一部 (足した最後の層など) を零初期化で 0 にできる. 部分モデルのノードでは, 中の項目は部分モデルを作るときに (外側の項目より先に) 行う
- 書き出すコード (`export_python`): 凍結, 零初期化, 共有, 評価の形は `__init__` の後ろと `train` に同じことを書く. 外部の重みはコードに書かず (読み込みにこのライブラリの付け替えと報告が要るため), その旨のコメントを書き, 注意 (`warnings`) を出す. 書き出したクラスの `state_dict` のキーは同じなので, このライブラリで読み込んだモデルの重みを保存して読ませる
- 定義とコードの境目 (ML_tester の方針): ここに書くのは 1 回の順伝播の計算とパラメータの状態まで. 損失, 更新の順 (部分ごとの学習率, 凍結を途中で外す段階的な解凍, 交互の更新), 繰り返しのサンプリング, 外部の仕組みは学習のスクリプトに残す

### 入力の例

- `shape` は書いたとおりの形 (バッチの次元も含む. グラフのデータでは `x` は `[ノード数, 特徴量]`, `edge_index` は `[2, エッジ数]`). 形の推定と確認にだけ使い, 組み立てたモデルは任意の形を受け取る
- `dtype` は `float32` (既定), `int64` など. 単語の番号, `edge_index`, グラフの番号 (`batch`) は `int64`
- `fill` は例の値の作り方で, `zeros` (既定), `ones` (注意のマスクなど), `arange` (位置の番号など)
- 例の形には 1 を使わない方がよい. 1 の次元はブロードキャストで他の大きさに合ってしまい, 形の誤りを見逃す (BatchNorm も学習時はバッチ 1 で失敗する)

### 名前の規則

- 入力, ノード, 出力, 部分モデルの名前は, 英字か `_` で始まり, 英数字と `_` だけからなる名前 (Python の予約語を除く)
- 書き出すコードで使う名前 (`self`, `torch`, `nn`, `ops`, `result`, `_pick`) を入力やノードに使うと, 組み立てと形の推定はできるが, コードは書き出せない (確認では注意 `export_name`. 出力の名前は書き出すコードでは辞書のキーなので対象外)
- 入力とノードは 1 つの名前の空間で, 同じ名前は使えない
- 組み立てたモデルの部品の入れ物 (`nn.ModuleDict`) の属性と同じ名前 (`type`, `float`, `training`, `keys`, `update` など) はノードに使えない. ノードの名前はそのまま部品の名前になり, `state_dict` のキー (`nodes.fc1.weight` など) にも使われる. そのため, ノードの名前を変えると, 前に保存した重みは読み込めない

### この形にした理由

- **グラフにする**: 残差のつなぎ方, Transformer の注意の分岐, GNN の `x` と `edge_index` のように, 実用のモデルの多くは一直線ではない. 一直線のリスト (`nn.Sequential`) から始めると, 後で形を変えることになる
- **ノードごとに入力のつなぎ先を書く**: エッジを別の一覧にするより, 1 つのノードを読めば何が入ってくるか分かり, 手で書いても読みやすい. GUI のエッジとは 1 対 1 に変換できる. GUI の位置はノードの `ui` に持つので, ノードの名前を変えても位置が迷子にならない
- **定義のファイルにする (コードを生成しない)**: 定義は検証, 差分, 再編集ができ, GUI と行き来できる. 他のプロジェクトにコードとして持っていきたい場合のために, 定義から Python のコードを書き出す機能も用意する

### 版

`format_version` は整数. 書かない定義は版 1 として読む (今の版ではなく. 新しい版ができても, 版を書かない古いファイルが直されずに読まれないように). 読み込むときに古い版から順に今の版に直し, ライブラリより新しい版はエラーにする. 保存するときはキーの順を決めて書き, ノードは書いた順のまま残す (GUI で保存しても差分が小さいように).

- 今の版は 2 (版 1 に「パラメータの状態」の 5 つの項目 `train`, `eval_mode`, `zero_init`, `weights`, `share` を加えた形). 版 1 の定義はそのまま読める (版 1 から版 2 に直すときに中身は変えない)
- **保存は書ける最も低い版**: `dump_spec` は, 版 2 の項目を 1 つも使わない定義を `format_version: 1` で書く (版 2 の項目を使う場合だけ 2). 版 2 のライブラリで開いて保存し直しても, 版 1 だけを読む古いライブラリ (学習のスクリプトなど) で読めるようにするため (ML-EDA の `dataset.yaml` の版 2 と同じ考え方). 読み込んだ定義の辞書は今の版 (2) になる
- 版 1 と書いた定義に版 2 の項目があれば, 読み込みで誤りにする (どの場所かを添え, `format_version: 2` にするよう案内する). 版を書かない定義も版 1 なので同じ. 版 1 だけを読む古いライブラリは版 2 の定義を「この版は読めない」で止まり, 知らない項目を黙って無視しない

定義は他のシステム (GUI, 学習のスクリプト, 将来の他の段階) との約束なので, 形を変える場合は次の決まりに従う.

- **版を上げる変更**: 定義の項目を足す, 消す, 名前, 意味, 値の型を変える. 確認は知らない項目を誤り (`unknown_key`) にするので, 項目を足すだけでも版を上げる. そうすると, 古いライブラリは知らない項目の誤りではなく「この版は読めない」と分かる誤りを出す. 新しいライブラリは, 古い版を今の版に直して読む (直す処理を `migrate` に足す)
- **版を変えない変更**: 部品を足す, 部品の引数を足す (どちらも登録簿の変更で, 定義の形は変わらない). `ui` の中に項目を足す (`ui` は画面のための自由な辞書で, 確認しない)
- 読む側が知らない項目を無視しないのは, 無視するとモデルが黙って違うものになり得るため (ML-Found の実験のディレクトリは, 読む側が知らない項目を無視する決まりで, そこが違う)

### 自作の部品のモジュール

研究の自作の部品 (層やまとまり) を, 画面 (ML-CreateArchitecture) や推論のアプリでも使えるようにする. 読み込むのは, アプリの起動の設定に書いたモジュールだけ. モデルの定義, 推論の一式, 保存したファイルに書かれた名前からは, 何も import しない.

- 入口: `register_units_from(module_names)`. モジュールの名前 (`my_lab.units` のような, 識別子を `.` でつないだもの. ファイルのパスは不可) の並びを受け取り, 順に `importlib.import_module` で読み込み, モジュールが宣言した部品を登録する. 結果はモジュールの名前ごとの, 登録した部品の名前のリスト (書いた順の辞書). アプリはこれをログに出す
- モジュールは, 次のどちらか (両方も可. `UNITS` が先) で部品を宣言する
    - `UNITS`: 並び. 要素は `nn.Module` のクラス (名前はクラス名) か, `register_unit` の引数の辞書 (`{"cls": MyBlock, "name": "my.Block", "outputs": ["a", "b"], "notes": {...}}`. `cls` は必須で, 他のキーは `register_unit` の引数の名前だけ. `module` と `overwrite` は書けない)
    - `register_units(register)`: 関数. `register` は `register_unit` と同じ引数 (`module` と `overwrite` を除く) を受け取る関数で, 呼ぶと部品を登録する (条件で部品を選ぶ場合など. `register_unit` を直に呼んだ部品はモジュールの部品にならない)
- 登録した部品は, 部品の一覧 (`describe_units`) の `module` に宣言したモジュールの名前を持つ (画面がモジュールごとにまとめるため). `register_unit` で直に登録した部品と組み込みの部品は空の文字
- 同じモジュールを 2 回渡した場合は, 読み込みも登録もし直さず前の結果を返す (アプリを同じプロセスで作り直す場合のため). 別のモジュールが同じ名前の部品を宣言した場合は, 後のモジュールでエラー (上書きしない)
- 誤りは, モジュールの名前を添えてそこで止める (`ValueError`. 名前の形が違う, 読み込めない (`ModuleNotFoundError` などの元の誤りを添える), 部品を宣言していない, `UNITS` の要素の形が違う, 登録できない (名前の重なり, 組み込みの頭), `register_units` が誤りを出した). 並びでない `module_names` (1 つの文字など) は `TypeError`. 起動の設定の誤りに早く気付くため, 一部だけ読み込んで続けることはしない. 止まったモジュールが登録した部品は登録簿から外す (同じプロセスで直して読み直せるように. 前のモジュールの部品は残る)
- 登録されていない部品を使う定義は, 確認 (`validate`) で `unknown_unit` の誤りになる. 文は「この部品 (`'my.Block'`) は登録されていません. 自作の部品なら起動の設定に足してください」に, 足し方 (部品を宣言したモジュールの名前をアプリの起動の設定に書いて起動し直すか, Python のコードで `register_units_from([...])` を呼ぶ) と書き間違いの候補を付ける. `get_unit` の `KeyError` の文も同じ案内を付ける. どちらも名前からモジュールを推し量って読み込むことはしない
- **安全**: 書いたモジュールは, 読み込んだときに任意のコードとして動く (Python の import と同じ). 信頼できるコード (自分や仲間が書いたもの) だけを書く. アプリは, 起動の設定を書ける人 (アプリを起動する人) だけがモジュールを選べるようにし, 画面や API や定義からモジュールの名前を受け取らない

### 口

- 入力の口は, テンソル (必須), 省略できるテンソル, 可変の数 (順に意味があるリスト, 口の名前は `xs`) のどれか. 手で書いた口の一覧があればそれを使い, 無ければ `forward` のシグネチャから取り出す (既定値の無い引数は必須, 既定値が `None` の引数は省略できる口, `*args` は可変の数. 真偽値や数の既定値を持つ引数は口ではなく `forward_params`)
- 呼び出しでは, `*args` より前の口と位置だけの引数の口は位置で (省略した場合は `None`), 可変の数の口は位置で並べ, それ以外の口と `forward_params` はキーワードで渡す. 真偽値を受け取る引数は, 既定値が `None` でも口ではなく `forward_params` にする
- 出力の口は, 1 つのテンソルを返すものは `out`. タプルや属性を持つ値を返すものは, 口ごとに取り出し方 (番号か属性の名前の並び) を持つ. 例えば `nn.LSTM` は `output` (`[0]`), `h_n` (`[1][0]`), `c_n` (`[1][1]`), `nn.MultiheadAttention` は `output` (`[0]`) と `weights` (`[1]`, `None` の場合もある)
- 引数の種類は型ヒントから決める (`int` と組の両方を受け取る `kernel_size` などは任意, `Literal` は選択肢). 種類が任意の引数も, 型ヒントの Union を分けて受け取れる種類 (`int`, `float`, `bool`, `str`, `list`, `null`. 例: `kernel_size` は int と list) を `types` に持ち, 確認で値の種類を確かめる (テンソルや関数を含む型ヒントは確かめない). 説明と範囲は, シグネチャから自動で取り出したものに (ML-Found の Optimizer の登録簿と同じ考え方), よく使うものだけ手で書いた説明を重ねる. 説明の無い引数は (自作の部品は `register_unit` の `notes` で書いたものが先), 引数の名前ごとの説明 (日本語. `in_channels` など多くのライブラリで同じ意味のもの) を使い, それも無ければクラスの docstring (Google 形式, NumPy 形式, Sphinx 形式) の説明をライブラリの言葉 (英語) のまま使う (reST の書き方は中の文字だけにし, 数式は LaTeX の命令と波括弧を除いた文字にし, 長いものは 300 文字で切る). ライブラリによって意味の違う名前 (`input_size`, `act_layer`) は docstring の説明を優先する. 説明の無い部品も, クラスの docstring の最初の文 (リンクと数式の書き方を除き, 160 文字まで) を説明にする
- 別の部品を引数に取るクラス (`nn.TransformerEncoder` など) は, 今は「使えない」として一覧に出す
- 入っていないライブラリの部品は, 一覧に「使えない (理由: ライブラリが無い)」として返す. GUI で選べないことを示せる

## 確認, 形の推定, 組み立て

- **確認** (`validate`): 定義の形, 名前, 部品の名前, 引数 (名前の誤り, 必須の不足, 範囲), 部品ごとの引数の組み合わせ (`invalid_combination`. 形の推定は重みを読まないので分からず, 組み立てで失敗するもの. 例: `tv.Model` の学習済みの重みのクラスの数と違う `num_classes`. 重みの情報はネットワークを使わずに読む), つなぎ先の存在, 口, 循環, 複数の入力をまとめる演算 (`op.Add`, `op.Multiply`, `op.Concat`, `op.Stack`) のつなぎ先が 1 つだけの場合 (注意 `single_input`. つなぎ忘れ), 使われないノードと入力 (つないだ先が出力に届かない入力は, そう伝える) を調べる. 最初の誤りで止めず, 全ての誤りと注意を返す (GUI でノードごとに示すため). 1 件は `{severity, code, message, node, location, subgraph}` (`location` は `params.out_features` や `inputs.edge_index`, `code` は決まった英字の識別子, `severity` は `error` か `warning`, `subgraph` は部分モデルの中の誤りの場合だけその名前で, それ以外は `None`). 定義を読み込めない場合 (YAML の誤り, ファイルが無い, ライブラリより新しい版) は `invalid_spec` の誤り 1 件だけを返す. ネットワークは使わない
- **組み立て** (`build_model`): `nn.Module` (`GraphModel`) を返す. ノードの部品を `nn.ModuleDict` に持ち, 前もって決めた順 (トポロジカル順. 同じ順位は定義に書いた順) に計算する. 重みは `state_dict` で保存して読み込む (モデルごとの `torch.save` は, 読み込みに `weights_only=False` が要る). 乱数の種を指定できる. 出力に届かないノードも組み立てて計算する (確認では注意)
- **一部の計算** (`GraphModel.compute(values, outputs=None)`): 組み立てたモデル (学習した重みを読み込んだもの) のまま, 求める出力に要るノードだけを計算する. 学習した VAE の復号器だけを潜在変数から呼ぶ (`model.compute({"z": z}, "recon")`), 2 塔のモデルの品物の塔だけで品物の埋め込みを前もって計算する (`model.compute({"item": item}, "item_embedding")`) のような使い方のため. `values` のキーは入力の名前か, ノードの出力の口 (定義のつなぎ先と同じ書き方で, `ノード` は最初の出力の口, `ノード:口` はその口. 例: `lstm:h_n`) で, 渡した値はその口の値の代わりに使う. その値だけから求まるノード (渡した口と, そこからしか要らない前のノード) は計算しない. `outputs` は定義の出力の名前 (1 つなら文字, 複数ならリスト. `None` なら全て) で, 結果は出力が 1 つでも出力の名前の辞書にする (求めた名前で受け取るため). 求める出力から, つなぎ先を前へたどり, 渡した値の所で止めて, 要るノードを決める (計算の順は `forward` と同じ). 要る入力が渡されていない場合は, どの出力にどの入力が要るかを添えて `ValueError` を投げる (「出力 recon の計算に要る入力 x が渡されていません」と, 途中のノードの値を渡すか要らない出力を `outputs` で除く案内). 入力にもノードにも無い名前の値, ノードに無い口, 定義に無い出力の名前も `ValueError`, `values` が辞書でない場合は `TypeError`. 要らない値は使わずに無視する. `forward` と同じく, 学習の形と評価の形 (`eval()`) と勾配の有無は変えない (VAE の再パラメータ化や Dropout は形で値が変わる). `model(...)` を通らないので, モデル自体に付けたフック (`register_forward_hook`) は呼ばれない (ノードの部品に付けたものは呼ばれる)
    - 部分の定義を切り出す形 (始まりのノードと出力を決めて別の定義にする) にはしなかった. 切り出した定義では `state_dict` のキーが元の一部になり, 読み込みに `strict=False` かキーの選り分けが要る. 学習で使った同じモデルを使えば, 重みもキーもそのままで, 定義の版も変わらない. 書き出すコードには入れない (書き出すコードは全体の `forward` だけ. 一部だけを呼ぶ場合は, このライブラリで組み立てたモデルを使う)
- **形の推定** (`infer`): 入力の例 (`shape`, `dtype`, `fill`) から値を作り, cpu で `eval()` と勾配なしで, ノードを 1 つずつ計算する. 各ノードの出力の口ごとの形と型 (`None` も可), パラメータ数 (全体と学習するもの. 共有した重みは 1 回だけ数える) を返す. 失敗したノードはエラーを, その先のノードは「前のノードの失敗で計算できない」を返す. 大きすぎるモデルでメモリを使い切らないように, 先に (meta デバイスで) パラメータ数を数え, 上限 (`max_params`. 既定 2 億) を超える場合は計算せずにパラメータ数だけを返す (`estimated_only` が `true`). meta デバイスで作れない部品があって前もって数えられない場合は, 注意 (`no_estimate`) を加えて計算する. 入力の例の要素数が上限 (`max_input_elements`. 既定 1000 万) を超える場合 (注意 `input_too_large`) と, 形 (`shape`) の無い入力がある場合は計算しない. 定義に誤りがあっても, 組み立ての途中で形を確かめられるように, 誤りのあるノード (つなぎ先の無い口, 引数の誤り, 部品を作れないものなど) とその先のノードだけを除いて計算する (誤りのあるノードは確認の誤りの文を持つ `error`, その先は `skipped`, `ok` は `false`). ノードに付かない誤り (入力の書き方など. 出力が無いこと, 出力のつなぎ先の誤り, 部分モデルの中の誤りは除く) がある場合は計算しない. Hugging Face のモデルの名前を確かめられない注意 (`unchecked_model`) は, 読み込んで計算できたノードでは除く. 結果は `ok`, `issues`, `nodes` (ノードごとの `status` (`ok`, `error`, `skipped`), `outputs`, `params`, `trainable`, `error`), `outputs`, `params`, `trainable`, `estimated_only`
- **書き出し** (`export_python`): 同じ計算をする `nn.Module` のクラスの Python のコードを書き出す. 既定では, このライブラリが無くても動くコードにする (使う演算 (`op.*`) と Hugging Face の部品のクラスの定義を `inspect.getsource` で書き写し, 部品を作る式を `Add(...)` のようにクラスの名前にする. 書き写したクラスが使う名前 (`torch`, `Any`, `Optional`, `importlib`) だけを読み込む. 書き写すクラスの名前が, 書き出すクラス (本体と部分モデル) や他に読み込むクラス (自作の部品) と重なる場合と, 書き出すクラスの名前が書き写したクラスの使う名前と重なる場合はエラー. クラスの中身を読めない環境 (ソースの無いインストール) では, 注意を出して読み込む行を残す). `standalone=False` では `from ml_modelcontrol import ops` などで読み込む. 同じモジュールから読み込む行は 1 行にまとめる. 自作の部品は, 登録したクラスのモジュールから読み込む行を書く (関数の中や実行したスクリプト (`__main__`) で定義したクラスは読み込めないのでエラー). `state_dict` のキーは `build_model` と同じにする. 出力の口の名前での取り出しは, 組み立てたモデルと同じにする. Hugging Face の出力 (辞書) は `.get` (無いキーは `None`) で書き, 型の分からない自作の部品の出力は, 辞書ならキー, それ以外は属性で取り出す関数 (`_pick`) をコードに置いて使う. 部品を作る行とノードを呼ぶ行は, 79 文字を超える場合に引数を折り返す (出力の辞書の行と, とても長い名前の行は超えることがある)

## 安全

- 部品は登録簿の名前だけで選ぶ. モデルの定義に import のパスやクラスを書く方法は作らない. 自作の部品の登録は Python のコードから行う. アプリでは起動の設定に書いたモジュールだけを `register_units_from` で読み込み (読み込んだモジュールは任意のコードとして動くので, 信頼できるものだけを書く), 定義に書かれた登録されていない名前からは何も import しない (「自作の部品のモジュール」)
- YAML は `yaml.safe_load` で読む. 引数は JSON の値だけ
- Hugging Face のモデルの外部のコード (`trust_remote_code`) は使わない (モデルの定義からも, ライブラリを使う側のコードからも有効にできない)
- 確認 (`validate`) はネットワークを使わない. Hugging Face のモデルの設定が手元に無い場合は, 確認できないことを注意で返す

## 外部のライブラリ

- 外部のライブラリは全て任意の依存 (clone したディレクトリで `pip install -e ".[geometric]"` のようにライブラリごとに選ぶか, `[all]` で全て. PyPI には公開していない). 入っていない環境でも, 残りの部品は使える. 入っていないライブラリは, よく使う部品だけを「使えない」として理由付きで一覧に出す
- 部品の取り込み方は 2 つ. (1) **クラスを集める**: ライブラリのモジュールの `nn.Module` のクラスを, PyTorch Geometric と同じくシグネチャから引数と口を取り出して部品にする (土台のクラス, 入れ物, 別名は除く. 引数に別の部品が必要なクラスは「使えない」). (2) **名前で作る**: torchvision と timm のモデルは数が多く, クラスより名前で選ぶ方が分かりやすいので, モデルの名前を引数に持つ 1 つの部品にする. 名前の候補 (`suggestions`) は一覧に付けるが, 候補以外も書ける (新しいモデルのため)
- 部品の名前は `<頭>.<クラス名>`. 頭はライブラリごとに決め (`tv` は torchvision, `audio` は torchaudio, `smp` は segmentation_models_pytorch, 他はライブラリの名前), 分類は `<頭>_<モジュール>` (`tv_ops`, `kornia_filters` など). 同じライブラリの複数のモジュールに同じ名前のクラスがある場合 (`kornia.augmentation.Normalize` と `kornia.enhance.Normalize` など), 先に集めたモジュールのクラスを `kornia.Normalize`, 後のモジュールのクラスを `kornia.enhance.Normalize` のようにモジュールの名前を挟んで区別する
- 名前で作る部品のモデルの名前の引数は, ライブラリの関数の引数の名前に合わせる (`tv.Model` は `name`, `timm.Model` と Hugging Face は `model_name`. 書き出すコードがそのまま関数の呼び出しになるため). Hugging Face の部品の名前は transformers のクラスの名前に合わせる. ただし `hf.AutoVisionModel` は, 画像を受け取る `AutoModel` (ViT などの本体) を文のモデルと区別するための名前
- 書き出すコードでは, ライブラリのモジュールを別名 (`from torchvision import ops as tv_ops` など) で読み込み, 違うライブラリの同じ名前のクラスが重ならないようにする
- 学習済みの重みを読む引数 (`pretrained`, `weights`, `encoder_weights` など) を部品ごとに持ち (`offline`), 形の推定ではその引数を「読まない」値に置き換える (`tv.Model` は `weights` と, 検出と領域分割のモデルの `weights_backbone`) (形は重みに依らず, 大きな重みの取得を避けるため). 組み立て (`build_model`) では書いた値のまま使う
- Hugging Face のモデルを名前で読む場合はネットワークを使う (形の推定でも設定の取得に使う). 確認では使わない
- 学習済みの重みを読む部品の一覧: `describe_units()` の部品ごとの `weights_params` (重みを読む引数の名前のリスト. `offline` のキー. 重みを読まない部品は空). GUI は, これが空でない部品にだけライセンスの欄を出す

### 学習済みの重みのライセンス

学習済みの重みを読むノードについて, 重みのライセンスを配布元の情報から自動で読み, 商用で使えるかを分けて, 使えないものと分からないものを警告する. 同じ情報で, 推論の一式に重みを写せるか (`redistributable`) と, 読んだ重みの版 (`pinned_revision`) も返す (ML-Inference が推論の一式を書き出すときに使う).

- 入口: `pretrained_info(unit, params, fetch=True)`. ノードの部品の名前と引数の値 (書いていない引数は既定値) から, 重みを読む場合は情報の辞書を, 読まない場合 (`pretrained: false`, `weights` が空など. 既定値を含めて `offline` の値と同じか, `null`, `false`, 空の文字) は `None` を返す. 登録簿に無い部品の名前は `KeyError`, 辞書でない `params` は `TypeError`. 確認 (`validate`) と形の推定 (`infer`) には入れない (ネットワークを使うので, 画面がノードを選んだときなどに別に呼ぶ)
- 返す辞書: `unit` (部品の名前), `library` (`huggingface`, `timm`, `torchvision`, `smp`, それ以外は部品の出どころ), `model` (書いたモデルの名前), `hub_id` (Hugging Face の置き場の名前. 分からなければ `None`), `revision` (求めた版), `pinned_revision` (Hugging Face が返したコミットの識別子. 読めなければ `None`), `license` (読んだライセンスの識別子. 複数ならカンマで並べる. 読めなければ `None`), `licenses` (識別子のリスト), `confirmed` (配布元の説明から読めたか), `status` (`commercial`, `noncommercial`, `unknown`), `redistributable` (真偽値), `gated` (申請制か), `alert` (警告するか. `status` が `commercial` でなければ真), `message` (画面にそのまま出す説明), `source` (どこから読んだか, 読めなかったか. 画面は `message` と並べて必ず出す), `url` (配布元のページ. 無ければ `None`)
- 配布元の情報の読み方 (部品ごと)
    - Hugging Face (`hf.*`): `model_name` を置き場の名前とし (`組織/名前` か `名前` の形で `..` を含まないものだけ. それ以外と, 版が `.` か `..` のものは読まずに `unknown`. 手元のディレクトリと同じ文にし, サーバーにディレクトリがあるかを文で分からせない. API の別の道をトークン付きで読まないため), Hugging Face の API (`/api/models/<名前>/revision/<版>`) のモデルの説明 (`cardData.license`. 無ければ `license:` のタグ) と, コミットの識別子 (`sha`), 申請制か (`gated`) を読む. `model_name` が手元のディレクトリの場合は配布元が分からないので `unknown`
    - timm (`timm.Model`, `pretrained: true`): timm のモデルの設定 (`pretrained_cfg`) の `hf_hub_id` を置き場の名前として Hugging Face から読む. 引数の `pretrained_cfg` が重みの名前の文字なら, timm と同じくモデルの名前の重みの名前 (`resnet50.a1_in1k` の `a1_in1k`) の代わりに使う. 辞書なら出どころを確かめられないので `unknown`. Hugging Face を読めない場合と置き場の名前の無いモデルは, timm の設定の `license` を参考に見せるが, 配布元の説明で確かめていないので `unknown` にする (どこから読んだかにそう書く)
    - segmentation_models_pytorch (`smp.*`, `encoder_weights` が空でない): ライブラリが符号化器と重みごとに持つ置き場の名前と版 (`repo_id`, `revision`) から Hugging Face を読む. timm の符号化器 (`tu-` の頭) は timm と同じ
    - 読む重みを名前と版以外で変える引数 (`pretrained_cfg_overlay`, `checkpoint_path`, `pretrained_url`, `weights_url`, `pretrained_path`. どの部品でも) が空でなければ, 配布元の情報と読む重みが合うか分からないので `confirmed` を偽にし (`unknown`), `source` に理由を足す. Hugging Face の部品は一覧に無い引数を受け取らず, 重みを変えるのは `model_name` と `revision` だけ (どちらも読む先に使う). segmentation_models_pytorch は `encoder_name` と `encoder_weights` を読む先に使う
    - torchvision (`tv.Model`): 重みに機械で読めるライセンスの情報が無いので `unknown` (「読めなかった」). 他のライブラリ (MONAI など) も同じ
- 分け方: ライセンスの識別子 (Hugging Face の書き方. 小文字) の小さな表をコードに持つ. 商用で使えるもの (`apache-2.0`, `mit`, `bsd-*`, `cc-by-4.0`, `cc0-1.0` など許諾の広いもの), 商用で使えないもの (`cc-by-nc-*` など), 識別子に `noncommercial` か `non-commercial` を含むもの (`fair-noncommercial-research-license` など) も `noncommercial`. それ以外は全て `unknown` (欄が空, `other`, 独自の条件 (`llama*`, `gemma` など), 利用の制限つき (`openrail*`), 条件の確かめが要るもの (GPL, `cc-by-nd`, `cc-by-sa` など)). 申請制の重みと, 配布元の説明を読めなかった重みは `unknown` (ただし `noncommercial` はそのまま. 申請制でも商用で使えないことは確か). ライセンスが複数ある場合は最も厳しいもの (`noncommercial`, `unknown`, `commercial` の順). `commercial` は「配布元がそう書いている」の意味で, 配布元の書いたライセンスが正しいかは確かめない (他の人が上げ直した重みもある). 表に無いものを商用で使えるとは言わない (間違って使える側に倒さないため)
- 再配布 (`redistributable`): `status` が `commercial` のものだけ真. 非商用のライセンスにも条件つきで再配布を許すものはあるが, 一式を商用で使う場合に備えて写さない側に倒す. 偽のものは, 推論の一式に重みを写さず, 出どころの名前と `pinned_revision` から読む
- 警告の文は日本語で, どこから読んだかを必ず添える (例: 「Hugging Face のモデルの説明から読んだ (置き場の名前)」「timm のモデルの設定から読んだ (配布元の説明では確かめていない)」「Hugging Face から読めなかった (置き場の名前: ネットワークの誤り)」)
- トークンと環境変数: 非公開のモデルと申請制のモデルの情報は, 環境変数 `HF_TOKEN` (無ければ `HUGGING_FACE_HUB_TOKEN`) のトークンで読む (transformers と同じ変数なので, 重みの読み込みにも同じものが使われる). トークンは返す辞書と文に入れず, 転送先には渡さない. `HF_ENDPOINT` で Hugging Face の置き場の URL を変えられる (ミラー). API を待つ上限 (10 秒) は, つなぐ, 読むなどのソケットの操作ごとのもので, 全体の上限ではない. `HF_HUB_OFFLINE=1` か `fetch=False` ではネットワークを使わず, 覚えた結果が無ければ「読めなかった (ネットワークを使わない設定)」にする
- 覚えておく (キャッシュ): Hugging Face の結果をプロセスの中に置き場の URL (`HF_ENDPOINT`), 置き場の名前, 版, トークンの hash ごとに覚え (トークンを変えたら読み直す. トークンそのものは覚えない), 読めた結果は 1 日, 読めなかった結果は 10 分の間は読み直さない (画面がノードを選ぶたびに読みに行かないため. 読めなかった場合は, つながった後に読み直せるように短くする). 覚える数は 512 まで (超えたら古いものから消す. 画面から打ちかけの名前が来ても増え続けないため). `clear_pretrained_cache()` で消す. ファイルには残さない
- テストはネットワークを使わない (Hugging Face を読む関数を差し替える)

## 課題の型への広げ方

部品の登録簿と定義から組み立てる仕組みは課題の型 (ML_tester の受け持ちの分け方) に依らない. 型ごとに要る形は, 演算, 受け持ちごとの雛形, 一部の計算 (`GraphModel.compute`), 定義の版 2 (「パラメータの状態」), 自作の部品のモジュールで書く.

- 受け持ちごとの雛形 (同梱の例 `vae`, `gan_generator`, `gan_discriminator`, `diffusion_denoiser`, `contrastive_encoder`, `two_tower_retrieval`, `policy_value`) は 1 回の順伝播だけを持ち, 損失, 更新の順, 雑音の加え方や環境との行き来は学習のスクリプトに残す. そのため, 損失に要る値 (VAE の平均と対数分散など) を出力に出し, 説明に学習の step で行うことを書く. GAN は 2 つの最適化手法で交互に学習するので, 生成器と識別器を別の定義にする. 対照学習は 2 通りの拡張をバッチの次元に並べて 1 つの符号化器に通す (共有を書かずに済み, 版 1 のまま読める)
- 出力の口は部品ごとに決まっていて引数では増やせないので, 分割 (`op.Chunk`) は名前を付けた複数の口ではなく, 等分した何番目かを 1 つ取り出す部品
